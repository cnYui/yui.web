# Admin 用户余额面板合并位置设计

## 背景

- `/shop/admin/` 当前有三个一级区域：
  - 「业务办理」：生成邀请码、生成重置码、补充 API key 池、充值审核、邀请码记录、API key 池记录。
  - 「用量监控」：token 概览、今日 / 本月收银、收银分析、用量明细、最近扣费记录。
  - 「日志导入」：usage JSONL 手动导入和自动导入状态。
- 用户需要新增一个能看到所有用户账户余额的面板。
- 已通过视觉草图对比三种位置：
  - A：合并进「业务办理」。
  - B：放进「用量监控」。
  - C：单独新增「账户余额」一级区域。
- 用户确认选择 A。

## 设计结论

用户余额面板合并进 `/shop/admin/` 的「业务办理」section。

推荐顺序：

1. 上方操作台：生成邀请码、生成重置码、补充 API key 池。
2. 充值审核。
3. 用户余额面板。
4. 邀请码记录 / API key 池记录。

## 原因

- 余额是账户台账状态，不是收入，也不是 token 用量。
- 管理员处理充值审核后，最常见的下一步是核对该用户余额是否更新；放在「业务办理」里路径最短。
- 「用量监控」已经承载 token、收银、消费排行和扣费记录；如果再放余额，容易把“账户余额”误读成“Shop 已赚收入”。
- 单独新增一级「账户余额」语义清楚，但会让 Admin 页重新变重，和 2026-06-12 已完成的「业务办理区合并」降噪方向冲突。

## 第一版范围

第一版只做只读面板，不做直接改余额。

面板需要展示：

- 汇总卡片：
  - 总余额。
  - 欠费用户数。
  - 欠费金额。
  - 待确认充值金额。
- 用户余额表：
  - 手机号。
  - 当前余额。
  - 欠费金额。
  - 待确认充值。
  - API key 状态或托管 key 数量。
  - 最近更新时间。

筛选和排序第一版保持克制：

- 可按手机号搜索。
- 可按余额状态筛选：全部、有余额、欠费、余额为 0。
- 默认排序优先展示欠费用户，其次按最近更新时间倒序。

## 交互

- 「业务办理」顶部统一刷新按钮同时刷新：
  - 邀请码 / API key 池记录。
  - 充值审核列表。
  - 用户余额面板。
- 充值审核确认或拒绝后，刷新充值审核列表和用户余额面板。
- 用户余额面板不复用「用量监控」的筛选器，避免把余额查询和 usage 查询耦合。

## 后端口径

- 新增管理员 session 接口更合适，例如 `GET /api/admin/account-balances`。
- 权限沿用 Admin 页面当前约束：
  - `requireAdminUsageAccess` 或等价管理员账户权限。
  - 不在浏览器使用 `ADMIN_TOKEN`。
  - 只读接口不需要 CSRF；后续如果新增直接调余额操作，必须使用 Same-Origin 和 CSRF。
- 数据源以 `account_balances` 为主，并关联：
  - `users`：保证已注册但余额行缺失的账号可被补齐或显示。
  - `orders` / `api_keys`：展示托管 API key 状态或数量。
  - `topup_requests`：统计待确认充值。

## 非目标

- 不把 Local / 未托管 usage key 当作 Shop 用户余额展示。
- 不在该面板里展示完整 API key。
- 不把余额汇总计入「今日收银 / 本月收银」。
- 不做直接充值、扣减、清零等写操作；这些后续需要单独设计审计和权限。

## 验收标准

- `/shop/admin/` 的「业务办理」section 中出现用户余额面板。
- 用户余额面板位于充值审核下方、邀请码记录 / API key 池记录上方。
- 面板能看到所有 Shop 用户账户余额状态。
- 业务办理统一刷新能刷新用户余额。
- 充值审核确认入账后，用户余额面板同步更新。
- 用量监控区不出现余额面板，仍只负责 usage、收银和扣费分析。
